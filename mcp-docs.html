Endpoint

  • Protocol: MCP Streamable HTTP
  • Authentication: API key in the X-API-Key request header

Tools

1. list_deals — browse merchant-published group-buy deals

Optional merchant_id filter. Merchants can only ever see their own deals' data.

2. create_group_buy — open a group from a published deal

Arguments: deal_id (string), organizer_name (string).

Returns a group_id and a shareable link. Unknown or unpublished deals are rejected — a group can only be created from merchant-published group terms.

3. get_group_status — paid-participant progress toward the goal

Arguments: group_id (string).

Returns the goal, paid-participant count, remaining spots, deadline, and status (open / filled). Progress reflects paid participants only.

Suggested end-to-end run (any MCP client)

  1. Call list_deals → note deal_handcare_001 (goal: 20 paid participants).
  2. Call create_group_buy with deal_id="deal_handcare_001" and organizer_name="Reviewer" → note the returned group_id.
  3. Call get_group_status with that group_id → paid_participants: 0, remaining: 20, status: "open".
  4. Call get_group_status with group_id="group_demo_002" → a pre-seeded filled group (15/15).
  5. Call create_group_buy with deal_id="deal_NOPE" → a clean rejection, demonstrating that groups require merchant-published terms.

Product boundaries

  • This demo uses sample data and tracks counts only; it does not take payments.
  • Merchants see only their own deals' data.
  • Status outputs describe observed counts; they make no causal claims about why a group did or did not fill.
